# System Monitor – Unix Log Monitoring Utility

## Objective

Build a Unix-based log monitoring utility that analyzes an application log file and generates a structured summary report, managed with a Git collaboration workflow and packaged as a Docker container.

## Project Description

`monitor.sh` is a Bash script that accepts a log file as an argument and:

- Validates the input (argument count, file existence, readability and empty files)
- Counts the total number of lines
- Counts lines containing `ERROR` and `WARNING` (case-insensitive)
- Finds the top 3 most frequent meaningful words
- Writes a structured report to `summary.txt` and prints it to the console

The script exits with code `0` on success and a non-zero code on failure, so it can be used safely in automation.

## Prerequisites

- Linux or Unix system with Bash 4.0 or later
- GNU core utilities (`grep`, `awk`, `sort`, `tr`, `wc`)
- Docker
- Git

Verify the installation:

```bash
bash --version
docker --version
git --version
```

## Manual Execution

1. Clone the repository:

    ```bash
    git clone https://github.com/tejasmayekar100/system-monitor.git
    cd system-monitor
    ```

2. Make the script executable:

    ```bash
    chmod +x monitor.sh
    ```

3. Run the script with a log file:

    ```bash
    ./monitor.sh logs/sample.log
    echo "Exit code: $?"
    ```

4. View the generated report:

    ```bash
    cat summary.txt
    ```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | Wrong number of arguments |
| 2 | File not found or not a regular file |
| 3 | File not readable |
| 4 | File is empty |
| 5 | Failed to write `summary.txt` |

## Docker Build and Run

Build the image:

```bash
docker build -t system-monitor:1.0 .
```

Run with the built-in sample log:

```bash
docker run --rm system-monitor:1.0
```

Run with log files from the host by mounting the `logs` folder:

```bash
docker run --rm -v "$PWD/logs:/app/logs" system-monitor:1.0 logs/sample.log
```

The image uses `ubuntu:22.04`, runs `monitor.sh` as its entry point and uses `logs/sample.log` as the default argument. The container stops after the report is generated and returns the script's exit code.

## Summary Output

Each run creates `summary.txt` in the following format:

```text
========================================
 LOG SUMMARY REPORT
========================================

Input File : logs/sample.log
Generated On : 2026-11-23 17:10:00
Generated By : monitor.sh

----------------------------------------
BASIC STATISTICS
----------------------------------------
Total Lines : 20
ERROR Count : 5
WARNING Count : 5
INFO Count : 2

----------------------------------------
TOP 3 FREQUENT WORDS
----------------------------------------
1. api          - 6
2. connection   - 4
3. database     - 4

----------------------------------------
END OF REPORT
----------------------------------------
```

| Field | Description |
|-------|-------------|
| Input File | Log file passed to the script |
| Generated On | Date and time of the report (`YYYY-MM-DD HH:MM:SS`) |
| Generated By | Script that created the report |
| Total Lines | Number of lines in the log file |
| ERROR Count | Lines containing the word `error` in any letter case |
| WARNING Count | Lines containing the word `warning` in any letter case |
| INFO Count | Lines containing the word `info` in any letter case |
| Top 3 Frequent Words | Most frequent meaningful words with their counts |

Meaningful words contain only letters, are at least 3 characters long, and exclude common stop words (such as `the`, `for`, `from`) and log levels (`info`, `error`, `warning`). Words with equal counts are listed alphabetically.

## Git Workflow

### Branching

- `main` holds stable, reviewed code and is protected from direct pushes.
- New work is done on separate branches created from `main`, such as `feature/log-monitor`.
- Contributors fork the repository and work on an `improvement/*` branch in their fork.

```bash
git switch main
git pull
git switch -c feature/<name>
```

### Pull Requests

- Each branch is pushed to GitHub and merged into `main` through a pull request.
- The pull request description includes a summary, the list of changes and the steps to test them.

### Review

- The repository owner reviews the changes and leaves comments on specific lines.
- If changes are needed, the owner requests them; the contributor pushes fixes to the same branch and the pull request updates automatically.
- Merge conflicts are resolved by the contributor by rebasing onto the latest `main` before the merge.

### Merge Strategy

- Owner feature branches are merged with a merge commit, which keeps each logical commit visible.
- Contributor pull requests are merged with squash and merge, which records one clean commit per contribution.
- Merged branches are deleted to keep the repository clean.
